1. Vue d'ensemble du projet

RescueNet coordonne une urgence médicale. Un opérateur du centre d'appels saisit l'appel ; la plateforme enchaîne automatiquement : dossier du patient → triage par intelligence artificielle → réservation d'un lit dans l'hôpital le plus proche → envoi de l'ambulance la plus proche, avec un suivi GPS simulé jusqu'à l'hôpital.

Le projet est une architecture microservices polyglotte : chaque service a son langage, sa base de données et son image Docker.

Flèches grises : appels HTTP. Flèche pointillée : enregistrement des services dans Eureka. Flèches rouges : messages RabbitMQ. emergency-service appelle aussi les 4 autres services avec OpenFeign (section 6).

Le déroulement d'une urgence

  1. L'opérateur remplit le formulaire (écran « Nouvelle urgence » du frontend).
  2. Le frontend envoie POST /api/emergencies avec un jeton JWT à l'API Gateway.
  3. La Gateway vérifie le jeton et le rôle, trouve EMERGENCY-SERVICE dans Eureka et lui transmet la requête.
  4. emergency-service orchestre (saga) : patient → triage → lit → ambulance, en appelant les autres services avec OpenFeign.
  5. Si l'ambulance est indisponible : le lit déjà réservé est libéré (compensation) et la réponse est un 503 clair.
  6. Le trajet de l'ambulance est simulé par dispatch-service qui publie des événements dans RabbitMQ ; à la fin, l'hôpital admet le patient, le dossier reçoit l'intervention et l'ambulance redevient libre.

4. Eureka — le Discovery Server

Rôle

Eureka est l'annuaire des services. Au démarrage, chaque service dit à Eureka « je suis TRIAGE-AI-SERVICE, joignable à telle adresse », puis envoie un signal de vie (heartbeat) toutes les 10 secondes. Quand un service veut en appeler un autre, il demande à Eureka l'adresse à partir du nom. Résultat : aucune URL ni port n'est écrit en dur pour joindre un autre service, et un service arrêté disparaît de l'annuaire au bout de 30 secondes.

5. L'API Gateway

Rôle

La Gateway est la porte d'entrée unique du système. Le frontend ne connaît qu'une adresse (http://localhost:8080) ; la Gateway :

  • route chaque requête vers le bon service (/api/emergencies/** → emergency-service, etc.) en utilisant Eureka (lb://NOM-DU-SERVICE) ;
  • sécurise : elle vérifie le jeton JWT et le rôle avant de transmettre (401 sans jeton, 403 si le rôle est insuffisant) ;
  • gère le CORS (autorise le frontend sur le port 4200) ;
  • répartit la charge si plusieurs instances d'un service existent.

6. OpenFeign — appels entre microservices

Rôle

OpenFeign permet à emergency-service d'appeler les autres services en déclarant une simple interface Java. On n'écrit ni URL, ni port, ni code HTTP : on écrit le nom Eureka du service et la signature de la méthode. La réponse JSON est convertie automatiquement en objet Java (DTO).

@FeignClient(name = "TRIAGE-AI-SERVICE", contextId = "triageClient")   // nom Eureka : aucune URL
public interface TriageClient {
    @PostMapping("/api/triage")
    TriageResponse triage(@RequestBody TriageRequest body);          // JSON <-> objets Java
}

7. Le point oublié : ce qui existe seulement en Java, sans port ni URL

À confirmer : vous avez écrit que vous ne retrouvez plus le nom d'une chose « qui se fait seulement en Java et qui n'a pas de port ni d'URL ». Je n'ai pas pu deviner avec certitude ; voici les deux candidats les plus probables, tous deux présents dans le projet. Si c'est autre chose, dites-le-moi et j'ajoute la section.

Candidat 1 — le client OpenFeign (« client déclaratif »)

C'est exactement la phrase de votre atelier : « Déclarer un client OpenFeign et appeler un microservice par son nom Eureka, sans URL ni port écrits en dur. » Il n'existe qu'en Java (Spring Cloud) ; il n'a ni port ni URL, seulement un nom (name = "TRIAGE-AI-SERVICE"). Voir section 6.

Candidat 2 — Spring Cloud LoadBalancer (répartiteur de charge côté client)

C'est le composant qui transforme le nom TRIAGE-AI-SERVICE en vraie adresse. Il demande à Eureka la liste des instances et en choisit une (round-robin). Il travaille à l'intérieur de l'application Java : il n'a pas de port ni d'URL propres.

8. Keycloak — authentification et JWT

Rôle

Keycloak est le serveur d'identité : il connaît les utilisateurs, vérifie leurs mots de passe, leur attribue des rôles et émet des jetons JWT signés. Les services n'ont jamais accès aux mots de passe : la Gateway vérifie seulement la signature du jeton et lit les rôles qu'il contient.

Le circuit d'une connexion

  1. Le navigateur ouvre le frontend ; keycloak-js redirige vers la page de connexion Keycloak (protocole OpenID Connect, code + PKCE).
  2. L'utilisateur saisit son identifiant et son mot de passe sur Keycloak.
  3. Keycloak renvoie un code ; le frontend l'échange contre un JWT (valable 15 minutes, renouvelé automatiquement).
  4. Chaque appel API porte l'en-tête Authorization: Bearer <jwt>.
  5. La Gateway vérifie la signature (clés publiques de Keycloak), lit realm_access.roles et applique les règles par rôle.

Comment le mettre en place soi-même (de zéro)

Méthode manuelle (pour comprendre) — console Keycloak, http://localhost:8180, compte admin / admin123 :

  1. Lancer Keycloak (docker compose -f docker-compose.infra.yml up -d keycloak).
  2. Menu en haut à gauche : Create realm → nom rescuenet → Create.
  3. Realm roles → Create role : OPERATEUR, puis ADMIN.
  4. Clients → Create client : Client ID rescuenet-frontend, type OpenID Connect ; « Client authentication » désactivé (client public) ; « Standard flow » coché.
  5. Dans ce client : Valid redirect URIs = http://localhost:4200/* ; Web origins = http://localhost:4200 ; onglet Advanced → PKCE Code Challenge Method = S256.
  6. Users → Add user (operateur, admin), onglet Credentials → Set password (« Temporary » désactivé), onglet Role mapping → Assign role.
  7. Côté Gateway : renseigner issuer-uri et jwk-set-uri (voir tableau) et écrire les règles dans SecurityConfig.java.
  8. Côté Angular : installer keycloak-js (npm i keycloak-js), écrire auth.service.ts, l'intercepteur et le guard.

Méthode automatique utilisée dans ce projet : tout le realm (rôles, comptes, client) est décrit dans keycloak/rescuenet-realm.json et importé au démarrage grâce à la commande start-dev --import-realm du conteneur. 9. Les rôles OPERATEUR et ADMIN

Qui est qui

  • OPERATEUR : employé du centre d'appels d'urgence. Il décroche, saisit l'urgence dans l'application et suit la mission. Ce n'est ni le citoyen (qui appelle par téléphone), ni une application propre à un hôpital.
  • ADMIN : responsable de la plateforme. Il a tous les droits de l'opérateur, plus l'accès au triage IA et la modification des dossiers patients.

11. RabbitMQ — communication asynchrone

Rôle

Les appels OpenFeign sont synchrones : on attend la réponse. RabbitMQ sert aux situations où l'on n'attend rien : un service publie un événement, d'autres le consomment quand ils le peuvent. Le producteur ne connaît pas les consommateurs : le couplage est très faible. Si un consommateur est arrêté, le message attend dans sa file.

12. Swagger et OpenAPI

Rôle

OpenAPI est un standard qui décrit une API REST dans un fichier (JSON) : routes, paramètres, formats, codes de réponse. Swagger UI est la page web qui lit ce fichier et permet de lire la documentation et tester les routes dans le navigateur, sans Postman. (Vous avez écrit « open IA » : il s'agit bien d'OpenAPI, sans lien avec l'intelligence artificielle.)

Comment se connecter à Swagger

Il n'y a pas de compte à saisir : on ouvre simplement l'adresse du service dans le navigateur.

Tester une route

  1. Ouvrir l'adresse (par exemple celle d'emergency-service).
  2. Cliquer sur une route (ex. POST /api/emergencies) pour la déplier.
  3. Cliquer Try it out, modifier le JSON d'exemple (copier scripts/demo-emergency.json).

13. Docker : pourquoi une image par service

Le problème que Docker résout

Ce projet utilise cinq langages (Java, Node.js, Python, C#, Go) et six technologies de données. Sans Docker, chaque ami devrait installer JDK 21, Node 22, Python 3.12, .NET 10, Go, Maven, puis configurer chaque base, et le projet « marcherait sur ma machine » seulement. Une image Docker contient le programme et tout ce dont il a besoin : le résultat est le même sur toutes les machines.

Pourquoi une image par service

  • Indépendance : on reconstruit, redémarre ou met à l'échelle un service sans toucher aux autres (principe du déploiement indépendant des microservices).
  • Isolation : chaque service a ses propres dépendances et versions, sans conflit.
  • Isolation des pannes : si un conteneur plante ou est arrêté, les autres continuent (démo : docker stop rescuenet-dispatch).
  • Images légères : Dockerfile en deux étapes (construction puis exécution) : l'image finale ne contient pas les outils de compilation (ex. dispatch : 55 Mo, frontend : 75 Mo).
  • Reproductibilité : même version partout, ce qui facilite les tests et la soutenance.

14. Docker Compose : pourquoi dans les microservices

Rôle

Avec 8 services applicatifs et 7 éléments d'infrastructure, soit 15 conteneurs, les lancer un par un avec docker run serait long et source d'erreurs. Docker Compose décrit l'ensemble dans un fichier et le démarre en une seule commande : docker compose up -d --build.

Ce que Compose apporte

  • Un réseau commun : les conteneurs se joignent par leur nom (discovery-server, rabbitmq, postgres-emergency…), sans adresse IP.
  • L'ordre de démarrage (depends_on + healthcheck) : bases et RabbitMQ d'abord, puis Eureka, puis les services, puis le frontend.
  • La configuration (variables d'environnement) : où se trouve chaque base, quel Eureka utiliser.
  • Les volumes : les données des bases survivent à un redémarrage.
  • Les ports publiés : identiques pour tout le monde (4200, 8080, 8761…).
  • Des commandes simples pour tout arrêter, voir l'état, lire les logs.

Les deux fichiers

FichierContenu
docker-compose.infra.yml7 conteneurs d'infrastructure : PostgreSQL, MongoDB, MySQL, SQL Server, Redis, RabbitMQ, Keycloak
docker-compose.ymlles 8 applications ; il inclut le fichier d'infrastructure (ligne 12 : include:)
Deux modes : Docker (tout en conteneurs, docker compose up -d --build) ou développement (infrastructure en Docker + services en processus locaux avec scripts\start-all.ps1). Ne pas utiliser les deux en même temps : les ports se chevauchent.

  1. Lancer Docker Desktop (menu Démarrer / Applications).
  2. Attendre que l'état en bas à gauche indique « Engine running » (icône verte).

Étape 3 — Construire les images et lancer les serveurs

docker compose up -d --build

  • Docker démarre les 15 conteneurs dans le bon ordre (bases, RabbitMQ, Keycloak, puis Eureka, puis les services, puis le frontend).

Suivre l'avancement :

Étape 6 — Scénario rapide à jouer

  1. Se connecter en operateur → bouton ✚ Signaler une urgence → Remplir avec la démo → 🚑 Lancer le dispatch.
  2. Sur « Suivi de mission » : triage ROUGE, hôpital, ambulance qui bouge sur la carte, frise jusqu'à Admis (environ 15 secondes).
  3. Menus Missions, Patients, Hôpitaux, Ambulances ; essayer /triage : « Accès refusé ».
  4. Bouton Se déconnecter, puis se connecter en admin : menu Triage IA, bouton Modifier le dossier d'un patient.
  5. Panne : docker stop rescuenet-dispatch, relancer une urgence → message « Service indispensable indisponible : DISPATCH-SERVICE » ; puis docker start rescuenet-dispatch.

Le scénario détaillé est dans docs/SCENARIO-DEMO.md.

Arrêter et relancer

docker compose down            # arrête et supprime les conteneurs (les données sont conservées)
docker compose up -d           # relance (sans reconstruire)
docker compose down -v         # arrête ET efface toutes les données (repartir de zéro)
